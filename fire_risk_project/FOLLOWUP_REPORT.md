# FIRE RISK 후속 개선 결과 — 2026-10-15

## 1. 분석한 구조와 작업 범위

- 화면: `frontend/src/main.jsx`가 새 평가·결과·저장 기록을 연결한다. 질문과 집계는 `assessment-inputs.jsx`, 결과·근거·사고사례는 `assessment-result.jsx`에서 표시한다.
- 서버: `api.py` → `watcher_input.py` / `risk_engine.py` → `storage.py`의 기존 흐름이다. 저장 레코드는 JSON/JSONB이므로 선택적 기상 스냅샷 추가에 테이블 마이그레이션은 필요하지 않다.
- 비교: `evaluation_history.py`, `previous-comparison.jsx`, `comparison.jsx`가 저장 당시 자료를 비교한다.
- 사고 원문: `data/03_사고데이터.csv` → 평가 시 `근거스냅샷.accidents`에 보존 → 화면에서 선택한다.
- 첨부 사진의 위치와 최신 React 소스가 일치했다. 현재 API는 H05 작업만 지원한다. 이번 작업에서 작업 선택 범위를 확대하지 않았다. 조건이 다른 H05 평가와 저장된 사례의 다른 작업 메커니즘을 비교하도록 수정했다.
- 기존 Streamlit 앱과 노트북은 이번 React 개선 대상이 아니다.

## 3. 사고사례가 한 건만 나오던 원인

기존 `EvidencePanel`은 **작업ID가 정확히 같고 검수완료인 사례만** 남겼다. H05에서 해당 조건을 만족하는 행이 A001(용인 성복동) 하나이므로 실제 입력 응답이 달라도 같은 사례가 나왔다. 사고 ID를 직접 하드코딩한 문제는 아니었다. 기존 필터는 위험조건이나 점수규칙을 사용하지 않았다.

새 `accident-matching.js`는 화재위험지수와 독립적인 화면 표시용 관련도만 계산한다.

| 관련 조건 | 정렬용 가중치 |
| --- | --- |
| 동일 세부 작업 | 4 |
| 용접/용단 점화원 유형 유사 | 2 |
| 주변 가연물 있음 + 사례의 가연물 조건 | 2 |
| 하부 가연물 있음 + 낙하 불티 조건 | 5 |
| 반대편 가연물 있음 + 열전도·복사 조건 | 5 |
| 불티 비산방지 미실시 + 사례에 명시된 미흡조치 | 4 |
| 화재감시자 미배치 + 사례의 미배치 기록 | 5 |
| 선택 물질과 사례 가연물의 명시적 용어 일치 | 용어당 3 |

다른 작업 사례는 **점화원 유사성과 현재 위험조건이 함께 맞아야** 표시한다. 동일 작업 사례는 기본 참고사례로 남을 수 있다. 따라서 가연물 없음·조치 실시 응답에서는 성복동 한 건만 표시될 수 있으며 이는 고정 출력 오류가 아니다. 미확인 응답을 위험조건 일치로 취급하지 않는다. 사유에는 실제 일치한 조건만 표시하며 사례 원문은 수정하지 않는다. 동일 관련도는 사고 ID로 정렬하여 표시 순서를 안정화한다.

현재 CSV는 총 **17건**, 그중 **검수완료 13건**, 분류확인필요 4건이다. 검수완료 ID는 A001, A003, A004, A006, A007, A008, A009, A010, A011, A014, A015, A016, A017이다. 일반적인 H05 주변 가연물 조건에서는 A001·A006·A008·A009·A011이 후보가 된다. 하부 가연물 조건은 A011, 감시자 미배치 조건은 A009 등의 우선순위를 높인다. 분류확인필요 4건은 기존처럼 제외하며 새 사고를 추가하지 않았다.

과거 평가의 사고 후보는 해당 평가의 저장된 스냅샷으로 한정한다. 당시 스냅샷이 없으면 현재 CSV로 대신 채우지 않는다. 관련도는 설명 가능한 용어·응답 규칙이며 검증된 사고 예측 모델이나 점수규칙이 아니다.

## 4. 기상청 연동과 저장

- 공식 자료: [기상청 API 활용가이드·지역 좌표 첨부](https://apihub.kma.go.kr/apiList.do?seqApi=10&seqApiSub=286), [공공데이터포털 단기예보 조회서비스](https://www.data.go.kr/data/15084084/openapi.do).
- 공식 `동네예보지점좌표(위경도)_260701.xlsx`에서 시·도와 시군구 대표지점 **274개**를 추출했다. 자유 입력 주소를 추측하거나 임의 좌표에 연결하지 않는다. 광역 대표지점을 고르면 UI에 `전체 대표지점`으로 표시한다.
- `GET /api/weather/regions`: 지역 목록. `GET /api/weather?region_id=...`: 서버에서 기상청 `getUltraSrtFcst` 호출. 기존 접속키 인증을 그대로 적용한다.
- 자료는 **초단기예보만** 사용한다. 실황처럼 표시하지 않으며 실황·예보를 혼합하지 않는다. 가장 가까운 미래 예보시각의 T1H, REH, PTY, RN1, SKY를 사용한다. 발표시각·예보 대상시각·자료 조회시각을 한국시간으로 구분한다.
- 공식 가이드에 따라 매시 30분 발표자료를 45분 이후 조회한다. 자정 전후 전날 날짜 전환을 처리한다. 응답 좌표·발표시각이 요청과 다른 자료는 사용하지 않는다.
- 결측·유효 범위 밖 수치는 `미제공`, 빈 응답·서비스 실패는 오류 안내로 표시한다. 임의 날씨나 다른 지역 날씨로 대체하지 않는다.
- 타임아웃 8초, 성공 결과 10분 캐시, 실패 30초 재호출 억제. 캐시는 서버 프로세스/따뜻한 Vercel 인스턴스별이다. 여러 인스턴스에 걸친 전역 호출량 제한은 아니다.
- 서버가 발행한 기상 스냅샷에 HMAC 서명을 붙인다. 평가 요청에는 지역 ID와 서명 토큰을 보내며 서버가 서명과 지역 일치를 확인한다. 클라이언트가 임의 기상값을 만들어 저장할 수 없다. 이 방식은 다른 Vercel 인스턴스에서도 같은 환경변수로 검증 가능하다.
- 평가 JSON에 `현장위치`, `기상정보`를 추가한다. 토큰 자체나 인증키는 평가에 저장하지 않는다. 조회 중·조회 실패·서명 불일치일 때도 기상정보 없이 평가는 저장할 수 있다.
- 평가 제출 중/완료 후에는 진행 중인 기상 조회를 취소하여 늦게 온 응답이 완료 결과를 초기화하지 않도록 했다.
- 과거 기록 조회 시 기상 API를 호출하지 않는다. 저장된 자료만 표시하고, 기존 기록의 누락 값도 안전하게 처리한다.

## 5. 인증키 설정과 남은 검증

현재 실행 환경에 `KMA_SERVICE_KEY`가 없다. 실서비스 응답·계정 호출한도·배포 네트워크 연결 검증은 하지 못했다.

1. [공공데이터포털 기상청 단기예보 조회서비스](https://www.data.go.kr/data/15084084/openapi.do)에서 활용신청 후 서비스키를 발급한다.
2. **API 서버** 환경변수 `KMA_SERVICE_KEY`에 일반 인증키(Decoding 권장)를 등록한다. 이미 URL 인코딩된 키도 한 번 디코딩하여 전송한다. 기상청 API허브의 별도 authKey와 혼용하지 않는다.
3. 로컬은 API를 실행하는 PowerShell 환경에 등록 후 서버를 재시작한다. 현재 백엔드는 `.env`를 자동 로드하지 않는다.
4. Vercel은 **백엔드 프로젝트** Settings → Environment Variables에서 사용할 환경에 등록한다. `VITE_*`, 프런트엔드 설정, 소스코드에 넣지 않는다. 기존 `DATABASE_URL`, `APP_ACCESS_KEY`, `CORS_ORIGINS`는 유지한다.
5. 배포는 별도 승인 후 진행한다. 새 API와 화면을 함께 반영하고 강남구·성남시·해운대구 등 실제 지역의 응답과 저장 후 복원을 확인한다.

기존 `vercel.json`의 `includeFiles: fire_risk_project/data/**`가 새 지역 JSON도 포함하므로 배포 구조 변경은 필요하지 않다. 인증키를 교체하면 교체 전 발행된 미저장 토큰은 유효하지 않아 기상정보 없이 저장될 수 있다. 이미 저장된 스냅샷은 영향을 받지 않는다.

## 6. 위험점수와 DB 보존

`07_기상데이터.csv`는 헤더만 있다. `08_점수규칙DB.csv`에 기온과 MSDS를 이용하는 **S016 인화점 여유** 규칙이 있지만 기준 상태가 미확정이며, 이번 조회값을 해당 규칙에 연결하지 않았다. 습도·강수에 새 점수를 부여하지 않았다.

`risk_engine.py`, `watcher_input.py`, `evaluation_history.py`, `storage.py`, 기존 CSV와 기존 평가 DB는 수정하지 않았다. 계산 데이터/엔진 해시 산출에 새 지역 JSON은 포함되지 않으므로 기존 비교 기준을 바꾸지 않는다. 테스트는 임시 DB를 사용했다.

## 9. 추가 작업

필수 후속 작업은 서버 인증키 등록과 실제 응답 검증이다. 행정구역 개편 시 공식 첨부 파일을 다시 내려받고 `python -m fire_risk_project.import_kma_regions outputs/kma-regions.xlsx`로 매핑을 갱신할 수 있다. 현재 사례 수가 제한되어 있으므로 더 많은 사례가 필요하면 공식 원문 검수 후 별도로 DB를 보강해야 한다.

Git 커밋, 원격 Push, Vercel 배포는 수행하지 않았다.

## 10. 2026-10-15 추가 연동 점검

후속 요청에서 기존 Vercel Production 변수명이 `KMA_API_KEY`라고 확인되어 실제 코드와 다시 비교했다. 이전 버전은 `KMA_SERVICE_KEY`만 읽어 등록된 키를 못 찾고 있었다. `weather.py`에서 `KMA_API_KEY`를 우선 사용하고 과거 설정 `KMA_SERVICE_KEY`를 보조로 지원하도록 수정했다. 따라서 배포된 API는 환경변수명을 적용하려면 재배포가 필요하다.

또한 기존 요청은 초단기예보 하나만 호출했다. 현재는 초단기실황(`getUltraSrtNcst`)과 초단기예보(`getUltraSrtFcst`)를 각각 요청해 `observed`와 `forecast`로 분리한다. 실황의 기온·습도·강수와 예보의 강수형태·하늘 상태를 서로 다른 기준시각으로 저장·표시한다. 한 API가 실패해도 나머지 응답은 표시하고, 둘 다 실패할 때만 오류를 표시한다. 두 요청은 지역별 10분 캐시를 공유한다.

개발 환경에는 Production 키가 전달되지 않아 실제 외부 기상청 호출은 여전히 검증하지 못했다. 최신 테스트에서 두 공식 엔드포인트 요청 형식·시각 계산·환경변수명 연결과 분리 저장은 모의 응답으로 검증한다. 실제 응답과 두 지역 확인은 API 프로젝트를 재배포한 다음 앱에서 수행해야 한다.
