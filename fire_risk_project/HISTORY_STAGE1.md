## 저장 및 식별

기존에는 `/evaluate`가 24시간 초안만 만들었습니다. 이제 계산 성공 후 기존 `evaluations` 테이블에 전체 결과를 저장한 다음 응답합니다. 입력 변경이나 질문 조회는 저장하지 않습니다. 저장 실패 시 완료로 표시하지 않습니다.

브라우저는 평가 요청별 UUID를 보내고 재시도에는 같은 UUID를 유지합니다. 서버는 동일 ID·입력의 재요청에 이미 저장된 결과를 돌려주며, 입력이 다르면 409로 거부합니다. 조회·새로고침·메뉴 이동은 평가를 생성하지 않습니다. 기존 저장 API는 이미 저장된 ID에 '이미 저장됨'을 반환하고, 이전 버전의 유효한 초안도 계속 저장할 수 있습니다. 수정하지 않은 입력으로 다시 평가 버튼을 누르면 같은 완료 결과를 유지합니다. 입력을 변경하면 다음 요청 ID가 생성됩니다.

현재 DB에는 별도의 현장 고유 ID가 없습니다. 현장명 앞뒤 공백 제거 및 연속 공백을 하나로 줄인 정확한 일치로 비교하며, 유사도나 대소문자 변환은 사용하지 않습니다. 기록에 현장ID가 있는 경우에는 이를 우선합니다. 같은 이름의 실제 다른 현장은 구분할 수 없으므로 구별되는 현장명을 사용해야 합니다.

같은 현장·같은 작업 ID의 기록 중 선택한 평가보다 이전인 가장 최신 기록을 사용합니다. 최신 기록의 계산 기준이 다르다고 더 오래된 기록으로 건너뛰지 않습니다. 시간대가 포함된 평가일시를 실제 시각으로 비교합니다. 새 평가의 일시는 마이크로초까지 보관합니다. 기존 초 단위 일시가 완전히 같은 기록은 평가ID로 순서를 안정화하며, 그 기록들의 실제 작성 선후는 기존 데이터로 복원할 수 없습니다.

## 비교 및 과거 결과 재현

계산 데이터·엔진 해시, 평가시점, 분모 및 질문 구성을 확인합니다. 누락/차이가 있거나 점수가 미산정이면 두 평가정보와 제한 사유만 보여주고 변화량·개선/악화 판정을 보류합니다.

질문별 분류는 저장된 규칙 계산 결과의 대표 가중점수 증감을 사용합니다. 응답 텍스트나 거리 숫자 자체로 판단하지 않습니다. 0점에서 양수로 바뀐 측정 항목은 새롭게 발생, 양수 유지 항목은 추가 개선 대상에 포함합니다. 미확인·제외·상세 누락은 0점으로 바꾸지 않습니다. 전체 지수 변화는 점수 단위이며 발생확률이나 위험 감소율로 표현하지 않습니다.

드롭다운은 저장된 전체 작업의 기록을 최신순으로 표시합니다. 현재 평가가 없는 새 세션에서는 최신 과거 평가를 선택합니다. 과거 평가를 현재 규칙으로 재계산하지 않으며, 점수·분석·조치·근거를 선택한 기록 하나에서 읽습니다. 빠르게 선택을 바꿀 때 이전 요청을 취소합니다.

새 기록에는 당시 법령/KOSHA 근거 및 사고사례 자료를 함께 저장합니다. MSDS 정보는 기존 기록에 없는 상태를 그대로 안내하며 DB를 수정하지 않습니다. 기존 기록에는 근거 스냅샷이 없어 당시 조치·근거·사고사례를 복원할 수 없다고 안내합니다. 기존 화면처럼 현재 자료를 과거 당시의 자료인 것처럼 대신 표시하지 않습니다.

사진과 코드 확인에서 작업명이 '용접·용단'으로 고정 표시되고 있었으나, 실제 H05 작업 DB에는 '철골부재 현장 용접접합'이 들어 있습니다. 새 결과에는 저장 당시 실제 작업명을 사용합니다. 과거 기록에 작업명이 없으면 누락 상태를 표시합니다.

## 저장 환경 및 제약

이력은 브라우저 로컬 스토리지가 아닌 API 서버 DB에 저장됩니다. Vercel은 React 정적 화면만 제공하고 API는 기존 Render 구성을 사용합니다. `DATABASE_URL`이 PostgreSQL 주소이면 기존 Postgres(JSONB) 어댑터를 사용하며, 없으면 서버 SQLite로 동작합니다. 이 작업의 로컬 환경은 SQLite였습니다.

Render Free의 로컬 SQLite 파일로는 재배포 후 영구 보관을 보장하지 않습니다. 기존 최소 구성대로 Render `DATABASE_URL`을 Supabase/Postgres에 연결해야 합니다. 운영 환경변수/실제 운영 DB 연결 및 운영 기록은 이번 작업에서 확인·변경하지 않았습니다. Postgres 실서버 통합 테스트는 수행하지 않았고 기존 저장 어댑터를 그대로 재사용했습니다.

기존 공용 접속 키 인증을 모든 신규 조회 API에도 유지합니다. 사용자별 소유권 분리는 원래 없으며 동일 접속 키 사용자끼리 기록을 공유하는 기존 방식입니다. 이력 목록·직전 조회는 현재 전체 기록을 읽는 방식이므로 대규모 기록에는 향후 색인/페이지 처리가 필요합니다.
